# 2~4인 멀티플레이

## 현재 구현 범위

- 방장 1명과 참가자 최대 3명. 최소 2명부터 공동 입장 가능.
- 이름, 접속 주소, 포트 입력과 방 생성·참가·접속 취소.
- 전원의 참가자 목록, 좌석, 준비 상태 동기화.
- 전원 준비 후 방장만 경기 시작 가능.
- 전원의 경기 화면 로딩 확인 후 `PLAYING` 상태로 전환.
- 같은 참가자 이름과 색상·좌석을 표시하는 임시 3D 경기 공간.
- 방장의 로비 복귀, 참가자 나가기·재접속, 방장 종료 처리.

추가로 첫 번째 아이디어의 차례·다트·점수·카드·얼굴 방해 동기화를 구현했다.
동시에 같은 방에 참가하고 다트는 좌석 순서로 던진다. 캐릭터 자유 이동은 후속 범위다.
경기 조작과 규칙은 [first_idea.md](first_idea.md)를 참고한다.

## 접속 방식

Godot 4.6의 `ENetMultiplayerPeer`와 고수준 RPC를 사용한다.
방장이 플레이어와 서버를 겸하는 방식이며 별도 서버 설치가 필요하지 않다.
기본 포트는 UDP `7000`, 전체 인원은 방장 포함 4명이다. 포트는 로비에서 변경할 수 있다.

| 상황 | 참가자가 입력할 주소 | 조건 |
| --- | --- | --- |
| 같은 PC의 여러 실행 창 | `127.0.0.1` | 한 창만 방 생성, 나머지 창은 참가 |
| 같은 LAN의 다른 PC | 방장의 내부 IP | 동일 포트, PC 사이 UDP 통신 허용 |
| 서로 다른 인터넷 환경 | 도달 가능한 방장 주소 | 공유기 UDP 포트 전달·방화벽 허용 등의 네트워크 설정 또는 향후 릴레이 |

같은 PC에서는 Godot `Debug > Customize Run Instances...`에서 여러 인스턴스를 활성화하고 F5로 실행한다.
각 창에 이름을 입력하고 하나만 방을 만든 뒤 다른 창은 참가한다. 모든 참가자가 준비하면 방장이 시작한다.

방 목록, 초대 코드, 자동 매칭, Steam 로비, 릴레이, 호스트 이전은 구현하지 않았다.
공유기와 Windows 방화벽 설정을 이 프로젝트에서 자동으로 변경하지 않는다.
검증은 같은 PC의 루프백 연결로 수행했다. LAN·외부 인터넷 도달성은 각 네트워크 환경에서 별도 확인해야 한다.

## 책임 분리

| 파일 | 책임 |
| --- | --- |
| `network/network_session.gd` | ENet 연결과 종료, RPC, 권한 검증, 타임아웃, 상태 전달 |
| `lobby/room_state.gd` | 인원 제한, 좌석 배정, 준비와 시작 조건, 방 상태 데이터 |
| `lobby/room_player.gd` | 참가자 한 명의 ID·이름·좌석·준비·로딩 상태 |
| `lobby/lobby.gd` | 사용자 입력을 signal로 전달하고 방 상태 표시 |
| `app/main.gd` | 연결 노드 유지, 로비/경기 화면 전환, 로딩 완료 확인 |
| `game/game.gd` | 확정된 참가자·좌석 데이터로 3D 공간 구성 |
| `ui/game_hud.gd` | 입장 상태와 참가자 표시, 로비 복귀·나가기 요청 |

로비 규칙은 `RefCounted` 데이터 클래스에 있고 네트워크나 UI에 의존하지 않는다.
연결은 `/root/Main/NetworkSession` 한 노드가 소유하며, 화면을 바꿔도 이 경로는 유지한다.
RPC 노드 경로와 스크립트가 모든 인스턴스에서 같아야 하므로, 연결을 경기 씬 안에 넣지 않았다.

## 상태 흐름

```text
미접속 → 방 생성 / 참가 → LOBBY
                            ↓ 2명 이상 + 전원 준비 + 방장 시작
                         LOADING
                            ↓ 현재 경기의 전원 로딩 확인
                         PLAYING
                            ↓ 방장 복귀 / 참가자 이탈
                          LOBBY

방장 종료 / 연결 실패 → 미접속
```

방장은 시작할 때 새 연결을 막고 `match_id`를 증가시킨다.
모든 참가자는 LOADING 상태를 받으면 경기 화면을 만들고 현재 `match_id`의 로딩 완료를 보낸다.
방장은 각 참가자의 완료 여부를 기록하므로 같은 응답이 두 번 와도 인원수가 증가하지 않는다.
과거 경기의 응답은 무시한다. 참가자 전원이 완료되기 전에는 PLAYING으로 전환하지 않는다.

## RPC와 권한

| RPC | 방향 | 검증 |
| --- | --- | --- |
| `_register_player` | 참가자 → 방장 | 실제 연결 ID, 중복 등록, 이름, 로비 상태, 인원 제한 |
| `_request_ready` | 참가자 → 방장 | 발신자의 등록 상태, 로비 단계. 자기 준비만 변경 |
| `_confirm_loaded` | 참가자 → 방장 | 발신자의 등록 상태, LOADING 단계, 현재 경기 ID |
| `_receive_room` | 방장 → 참가자 | `authority` RPC로 방장만 호출 가능 |

중요한 방 상태는 `reliable`로 전송한다. 변경 시 방장이 작은 전체 스냅샷을 전송한다.
최대 4명인 로비에서는 델타 복구 로직보다 이 방식이 단순하고, 뒤늦게 참가한 사람도 현재 상태를 바로 받는다.
클라이언트는 임의의 플레이어 ID를 요청에 넣지 않는다. 방장은 `get_remote_sender_id()`로 실제 발신자를 판단한다.
경기 시작과 전체 로비 복귀는 클라이언트용 RPC로 공개하지 않았다.

## 연결 해제와 대기

- 접속·등록이 8초 안에 완료되지 않으면 접속을 종료하고 다시 시도할 수 있다.
- 경기 화면 로딩이 10초 안에 완료되지 않으면 방장은 전원을 로비로 돌려보낸다.
- 경기 입장 이후 참가자가 나가면 해당 플레이어를 제거하고 남은 인원은 로비로 돌아간다.
- 로비로 돌아올 때 준비와 로딩 상태를 초기화한다. 빈 좌석은 재접속한 참가자에게 재배정된다.
- 방장이 나가면 방이 종료된다. 참가자는 연결·경기 화면을 정리하고 초기 로비로 돌아간다.
- 시작 중·경기 중 새 참가자 접속은 거부한다.

## 경기 기능 연결

`Main/Game/MatchController`가 경기의 reliable RPC를 처리한다.
투척 입력은 로컬에서 받고 방장에게 요청한다. 방장은 현재 차례·입력 범위·경기/턴/요청 ID를 검증하고 결과를 계산한다.
다트 비행 사건과 공개 경기 상태를 전원에게 전달하고, 카드 후보·사용 예약은 본인에게만 전달한다.
방장이 턴·카드·비행·정산 시간을 관리하고 각 화면이 표시와 장치 연출을 재생한다.
움직이는 캐릭터를 구현할 때는 이동 복제와 보간을 추가한다. 지금은 고정 좌석이라 지속적인 위치 전송을 하지 않는다.

## 검증

`tests/run_multiplayer.py`는 Godot 실제 프로세스를 띄우고 게임의 앱 씬과 ENet 연결을 사용한다.
상태 비교뿐 아니라 각 앱의 실제 Game 생성·제거, 참가자 표시 수, 로비 표시도 확인한다.
별도의 로딩 지연 참가자로 시작 장벽, 이전/중복 응답, 로딩 타임아웃을 검증한다.
실행 방법은 [README](../README.md)의 자동 검증 항목을 참고한다.
첫 경기 전체 검증은 `tests/run_first_idea.py`로 수행한다.

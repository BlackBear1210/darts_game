# 경기 시작 대기 없애기 — 경기 화면 재사용 (2026-11-18)

사용자 요청: "만약 기다리는 걸 없애려면 즉, 방생성후 대기 시간을 없애려면 어떤 작업을 해야하는지 알려줘봐" → 안내 뒤 "1번만 고쳐보자".
1번 = 경기를 시작할 때 경기 화면을 지우고 새로 만들지 않기.

## 방 만든 뒤 기다림 (11-18 창 모드로 잰 값)

| 단계 | 왜 기다리나 | 얼마나 | 이번 |
|---|---|---|---|
| 방 만들기 → 라운지 화면 | 경기 화면(펍·오락실 방)을 처음 짓는다 | 펍 약 1.0초 + 첫 그리기 0.4~0.5초 · 오락실 1.5~2.1초 + 첫 그리기 0.7~1.0초 | 그대로 |
| **앉아 Enter(준비) → 경기 시작** | **경기 번호가 바뀌면 화면을 통째로 지우고 다시 지었다** | **펍 1.2초 · 오락실 1.9초 멈춤** | **고침 → 0.06초** |
| 카드 확인 | 규칙(`MatchCards.VIEW_SECONDS`) | 5초 | 그대로 |
| 걸어가 앉고 Enter | 사람 조작 | — | 그대로 |

## 원인

- `app/main.gd` `_refresh_screen` 이 두 경우에 경기 화면(`game.tscn` — 방·사람·소품·HUD 전부)을 지우고 새로 만들었다.
  - 경기 번호(`match_id`)가 바뀔 때 = 경기 시작.
  - 방이 로비인데 경기 상태가 대기(WAITING)가 아닐 때 = 경기 끝나고 로비로 돌아오기.
- 실제로 새로 해야 하는 것은 경기 상태(점수·손패·차례)뿐인데, 방 전체를 다시 짓느라 화면이 멈췄다.

## 고침

- `app/main.gd`: 라운지 방이면 `_remove_game()` 대신 `_game.begin_match(room)` 을 부른다.
  - 전용 서버는 예전처럼 새로 만든다. 경기마다 계정 기록(`_backend.watch_match`)을 새로 묶어야 하기 때문이다.
- `game/match/match_controller.gd` 새 `reset_match(room)`: 경기 상태(`MatchState`)를 새로 만든다.
  - 비우는 것: 카드 담당(`cards`) · 알림 · 차례/단계 시간 · 날아가는 한 발 · 과녁 효과 시간 · 요청 기록 · 무효 카드 나눔 표시.
  - 그대로 두는 것: 연결(session 신호) · 규칙(`config`) · 내 번호 · 요청 번호(`_request_number`, 계속 올라가야 한다).
- `game/game.gd` 새 `begin_match(room)`: `reset_match` 를 부르고 화면에 남은 지난 경기 흔적만 치운다.
  - 꽂힌·날던 다트, 과녁 배치·숫자 고르기 표시, 쓰러진 사람 일으키기·밀려나기, 스턴, 1인칭 손 반동.
  - 킬로그 반응 기억(`emotes._seen_feed`), "카드 받을 때 한 잔" 라운드 기억(`lounge._last_deal`) → 새 경기 1라운드에도 반응한다.
  - 봇 수다·헤클링 담당(`bot_social`)은 새로 붙인다(만들기는 `_make_bot_social` 로 묶음).
  - 경기 시작이면 모두 테이블에 앉힌다(예전 새로 만들 때와 같다). 마우스를 다시 잡는다.
- 움직임 번호: **받는 쪽만** 처음으로 돌린다(`_last_motion_sequence = -1`, 방장이 받은 조작 `_controls` 비우기).
  - 보내는 쪽 번호(`_motion_sequence` · `_sequence` · `_request_number`)는 계속 오른다.
  - 그래서 손님은 화면을 재사용하고 전용 서버는 새로 만든 경우에도 움직임이 끊기지 않는다.
- 이어지는 것: 라운지 소품·음악·취기(예전엔 `_lounge_memory` 로 옮겨 담던 것) · NPC · 사람 위치 · 차림.
  - 로비로 돌아오면 앉아 있던 사람은 그대로 앉아 있다 → Enter 만 누르면 다시 준비된다.

## 같이 고친 것 — 화면 없는 실행에서 미리 읽기 오류 (11-17 밤 2 에 생긴 것)

- 여러 명 시험(`tests/run_lounge.py`)의 손님 로그에 엔진 오류 9개("Attempting to initialize the wrong RID" 등). 위치는 `app/asset_warmup.gd scene()`.
- 원인: 어제 넣은 미리 읽기·타이틀 펍 뒤에서 읽기가 화면 없는 실행(헤드리스: 시험·전용 서버)에서도 여러 스레드로 읽었다.
  - 그때 쓰는 엔진의 가짜 그리기 장치(dummy)는 여러 스레드가 동시에 메시를 만들면 깨진다.
  - 창 모드(진짜 그리기 장치)는 괜찮다 — 창 모드 측정에선 오류가 없었다.
- 고침: 화면 없는 실행에서만 바로 읽는다(`app/asset_warmup.gd start` · `lobby/lobby_backdrop.gd _ready`). 창 모드 게임은 그대로.

## 잰 값 (창 모드, 같은 PC — 측정 도구는 저장소 밖)

| 앉아 Enter → 경기 시작 | 전 | 후 |
|---|---|---|
| 펍 | 1.2초 멈춤 | 0.05~0.06초(한 프레임) |
| 네온 오락실 | 1.9초 멈춤 | 0.05~0.06초 |

- 펍·오락실 번갈아 4번 모두 같은 경기 화면이었다(새로 만듦 = false).
- 그 뒤 카드 확인 5초 → 첫 다트 차례는 그대로다(규칙).

## 시험

- 확인용 시험 `test_match_reuse.gd`(헤드리스, 커밋 안 함 — 아래 "정리"): 싱글 라운지 방에서 경기 1 → 점수·꽂힌 다트·과녁 배치·쓰러진 봇·킬로그 흔적을 일부러 남김 → 로비로 → 경기 2.
  - 세 번 모두 같은 경기 화면인지, 로비에서 흔적이 다 지워졌는지, 경기 2 가 새 번호·1라운드·새 카드 7장·다트 차례로 가는지, 지난 경기에 쓰러졌던 봇이 실제로 던지는지, 엔진 오류 0 인지 봤다.
  - 옛 `main.gd` 로 돌리면 "경기 1 시작 때 경기 화면을 새로 만들었다"로 FAIL, 새 코드는 PASS.
- `tests/run_lounge.py`(실제 연결 방장+손님 3프로세스, 팀 공용 시험 — 남김): 끝에 **같은 화면에서 두 번째 경기**를 붙였다.
  - 로비로 돌아와도 앉아 있음 → 둘 다 준비 → 경기 2(번호 +1 · 점수 0 · 카드 7장) → 다트 차례 → 손님 카드 고르기 → 손님 일어나 걷기(방장·손님 화면 모두에서 움직임).
  - 앞부분 "두 화면 방 정보가 같다" 비교가 손님 차림(look)이 한 박자 늦게 오는 순간에 걸려 가끔 실패하던 것 → 같아질 때까지 기다리게 고침.
  - 결과: PASS, 세 프로세스 로그 엔진 오류 0.
- 전체 헤드리스 시험: 아래 "검증" 참고.

## 못 한 것

- 사람이 직접 창 모드로 경기 → 로비 → 다시 경기 해 보기(시험·측정만 했다).
- 전용 서버 + 손님 조합(`tests/run_dedicated.py`)은 내보낸 실행 파일이 있어야 해서 돌리지 않았다. 코드로는 받는 쪽 움직임 번호를 처음으로 돌려 맞췄다.
